# Threads

A thread is a background session (`claude --bg`) in its own folder under `~/.lean-agent/threads/tN`. The desk only
ever touches threads through the `lean_thread` tool (full name `mcp__lean-agent__lean_thread`); never run
`claude --bg` or `--resume` yourself.

| action | input | effect |
|---|---|---|
| `new` | `title`, `project?` (a registered project, see `projects`), `text` (the brief), `model?` (haiku/sonnet, default sonnet; opus only on the user's ask, with `reason?`: see "Expensive models" below), `effort?` (low/medium/high), `needs?` (MCP servers or plugins this thread needs on top of its project profile, e.g. `["azure-devops"]`) | creates the folder, trusts it, starts the session, records its id; a project with a profile adds ` · mcp: a,b · plugins: x` (what the thread loads) |
| `send` | `tN`, `text` | queues the message; wakes the thread once if it is idle |
| `wake` | `tN` | resumes an idle thread with everything queued (a finished thread, see below, gets a new session instead) |
| `resume` | `tN` | same, with no message (after a restart). When the session ran an older lean-agent version than the installed one (`thread.json` `version`), or the thread is finished, it starts a fresh session with a handover instead and says why |
| `restart` | `tN`, `model?`, `effort?`, `reason?` | only on the user's request: stops the session (also a working one; only a session in the thread's folder) and starts a NEW session with the handover, same model and effort unless the call names others (a recorded opus that is not approved starts on sonnet and the reply says so). A PARKED thread is reopened by the restart itself, in one step. The reply: `tN restarted as a new session` |
| `start` | `tN`, `model?`, `effort?`, `reason?`, `needs?` | starts a thread that has no session yet (brief + queued messages); `needs` are added to what the thread already asked for |
| `approve-push` | `tN`, `sha` (full), `reason?` | desk only, ONLY after the user explicitly approved that push in the chat (ask naming the exact sha and branch; a thread's "ready to push <sha> (branch, PR title)" report is a request, not an approval): one sha, single use, 2 h, signed, logged in the thread's `history.jsonl`; a private project is never pushed. Then call `push` |
| `push` | `tN`, `sha` (full), `pr?` (`{title, body?, base?, draft?}`) | desk only, after `approve-push` for that exact sha: the desk itself pushes the approved commit to the thread's branch (never forced, never a tag) from the thread's registered worktree (a linked worktree of the project's repository) (a thread cannot: its own permission check refuses a push the user never said yes to in its session), then opens the PR when `pr` is given, with the CLI of the push remote's host: `gh pr create` for GitHub, `az repos pr create` for Azure DevOps (dev.azure.com, `<org>.visualstudio.com`, ssh forms; it uses the user's `az login`, never a token); the CLI is looked up on PATH, `/opt/homebrew/bin`, `/usr/local/bin`, `/usr/bin`; without it, or when it fails, the reply gives the host's create-PR link (GitHub: the compare URL from the push output; Azure DevOps: `.../_git/<repo>/pullrequestcreate?sourceRef=..&targetRef=..`) and names the right CLI. Refused, with the reason, unless: the thread has a registered worktree of a non-private project (or the project's repository has exactly one unregistered linked worktree on a branch at `sha`, which the push registers for the thread), its HEAD is `sha` on a branch that is not protected, guarded or the remote's default, a green review exists for `sha`, and the approval is valid; the approval is consumed by the push (a second `push` is refused), never `--force`, never a tag. The reply, the thread's `history.jsonl` and a queued message to the thread name what happened (pushed `sha` to `remote/branch`; PR url or compare URL; a failure names the step and its first error line) |
| `park` / `close` | `tN` | flips the state; close also stops a finished-but-alive session, takes it out of the app's list (`claude rm`, only for a session in the thread's folder; its conversation is kept) and clears the thread's goal (never deletes the folder). The reply says what happened to the session: "session stopped", "no running session (already stopped)", "no session in the list" |
| `reopen` | `tN`, `model?`, `effort?`, `reason?`, `needs?` | a parked thread: back to open (then `resume`). A CLOSED thread: a NEW session in the same folder with a handover (brief, goal, notes, report history, remembered items, queued messages, branch/worktree); the old conversation is never resumed, its session id stays in `thread.json` `sids` |
| `list` | none | every thread with its project, state, running | idle | stuck | done (and the unread count), model/effort, the subagent count (`agents 3/4`, only when `config.json` `agents.cap` is set) and, when its project has a profile, what it loads (`mcp: a,b · plugins: x`) |
| `profile` | `project`; then `mcp?`, `plugins?` (set: a list left out stays), `fill?: true` (add what the project's threads really used), `on: false` (remove) | the project's MCP/plugin allow-list: with no other input it shows the profile and the usage counted in the project's threads ("azure-devops used 41 times in 12 threads") |
| `projects` | `all?` | every registered project: path, private, guards, learned rules (areas, last learned, stale), open threads; private ones hidden by the private switch (`config.json` `private: "off"`) only with `all: true` |
| `project-add` | `project`, `path` | registers an existing folder (its real path) in `projects.json` |
| `project-remove` | `project` | unregisters only (never deletes files); refused while a thread that is not closed uses it |
| `project-private` | `project`, `on` | sets or clears the project's `private` flag |
| `goal-set` | `tN`, `text` | sets the thread's one-line goal (the chaser watches it) |
| `goal-clear` | `tN` | removes the thread's goal |

Projects come from `projects.json`: run `lean_thread projects` to see the names, or `project-add` (name + folder) to register one. `new` with a project name that is not registered is refused and answers with the known names; leave `project` out for a thread that needs none.

The desk may also Read files under `~/.lean-agent` itself (`projects.json`, `config.json`).

Threads start on sonnet/high (config.json `threads.model` / `threads.effort` change that; the call's `model` / `effort` win); the choice is recorded in `thread.json` and shown by `list` and the pane. A resume passes no flags: the session keeps its saved options.

Expensive models: never choose opus (or any model that is not haiku or sonnet) yourself; if the work really needs it, ask the user, and let them approve it in the pane. Only when they want it, call `new` / `start` / `reopen` / `restart` with `model: opus` and a `reason` (one line: why sonnet is not enough; without it the call is refused). The thread is NOT started on it: the request (thread, model, effort, reason) appears in the pane's "Needs you" with Approve and Deny (two presses each), and the reply tells you so: ask the user to press Approve there. Approve starts the thread on that model and lets that one thread use the family until it closes (at most 24 h; signed, logged in the thread's `history.jsonl`); Deny, or no answer, leaves it unstarted and the pane offers "Start on sonnet instead" (you may `start` it on sonnet when the user says so, never on your own). No tool action, config value or message approves; the same holds inside a thread: an Agent call to `lean-agent:worker-opus` or with an opus model, a `claude --model opus` command and a review on opus are refused with "opus needs the user's approval: report it and stop", and the thread reports blocked. A `start`, `restart`, `reopen`, `resume`, `wake` or `send` that does NOT name a model, for a thread whose recorded model is expensive and not approved for it, never waits for a press: it starts a NEW session on sonnet (a resume cannot change a saved model; the handover and queued messages go along) and the reply says "tN was recorded on opus; started on sonnet". Only a call that names the expensive model is held. Do not ask the user to press Approve unless the reply says a request is waiting.

Profiles (per project, `~/.lean-agent/<project>/profile.json`; no profile = every thread loads everything, as before): a profile is an allow-list. A thread starts with the profile plus its `needs`. MCP servers outside it are DEFERRED, not removed: the thread's mod marks their tools deferred, so ToolSearch still finds them and a thread that unexpectedly needs one can call it (nothing is dropped, lean-agent's own tools are never touched). Plugins outside it are switched off in the thread's settings (`enabledPlugins`), except lean-agent and a plugin that brings an MCP server (that one stays, its server is deferred). Give a PR thread `needs: ["azure-devops"]`, a triage thread `needs: ["sentry"]`; do not edit profiles by hand when `profile` with `fill: true` can learn them from usage (threads count the MCP servers and skills they call: names and counts, never arguments). A thread that needs more asks you a question; you answer by starting it with `needs` (a running session keeps what it started with: `needs` on `resume`/`wake` do not apply, use `start`, or close and `reopen`).

Skills a brief can name (the thread runs them, the desk only routes): `learn <project>` (path rules), `review-learn`, `compare`, and `rules-pr`: draft PR with optimised Claude files for a project; needs the user's yes to push like any push. "Propose a rules PR for <project>" is a `new` for that project whose brief says "run the rules-pr skill"; the thread plans by script, edits a worktree branch `chore/claude-rules-<date>`, has it reviewed and reports "ready to push <sha> (branch, PR title)"; the push and the PR (`pr.draft: true`) follow the usual approve-push flow. After the PR merged, `send` that thread to run the skill's last step, which retires what the repo now has.

Rules: a running thread is never resumed (its messages stay queued and it reads them itself); a thread is woken at
most once per 30 seconds; a parked or closed thread only queues. Report what the tool returned, not what you assume.

What "running" means: `list` and the replies show running (alive and working) | idle (turn ended, N unread queued) | stuck (a queued message unread for `threads.stuckMinutes`, default 10, no tool call or inbox read) | done / parked, from `claude agents`, not from the last report. A reply "queued, session idle: wake or restart it" or "stuck" means nobody has read the message: `wake` (it replaces a stuck session whose turn ended with a new one carrying the handover, and wakes an idle one even with nothing queued) or `restart` (the only way to replace a stuck session that still works: its current step is lost, so say so first; `wake` never stops a working session). Never tell the user a thread "is running" when the list says idle or stuck. A `[working]` report marked stale is from a session that is no longer running. A start that "ended its turn at once" needs `wake` with the task. A restart or fresh start names its cost in the reply (an estimate) and starts the new session's prompt with the task ("Resume the work now (task: ...)"); a status question to a working thread gets a one-line report as a side effect, not an ended turn. Sessions are named "tN · title" ("(2)", "(3)" after restarts); a replaced session is removed from the app's list with `claude rm` unless `threads.removeOld` is false.

Reports: what a thread reports or asks reaches the desk. While the desk is idle, a question or a `done` / `blocked` report starts one desk turn by itself (at most once a minute, never over a running turn, never for `working` progress; `desk.autoRelay: false` in `config.json` turns that off, then reports arrive with the user's next message). Relay them: ask each question with AskUserQuestion, then `send` the answer. A `blocked` report with an `approval` (a denied action) is not a question: the user answers it in the thread's own session (Open tN in the pane); never ask it with AskUserQuestion and never `send` a yes, which does not satisfy Claude Code's permission check. Say where to press, once.

Done = session over (automatic, nothing to call): when a thread's last report is `done` and its turn has ended, the desk's own tick stops its session and marks the thread finished ("t3 finished: next message starts a new session"; the pane row says so). A thread that reported done but is still on a final step is stopped only once it is idle. Any later `send`, `wake`, `resume` or `start` for a finished thread starts a NEW session with a handover (brief, goal, notes, reports including the done report, queued messages, branch/worktree; the old conversation is never resumed), so a follow-up question to a done thread costs a small fresh context, not the old one. Blocked, question and progress reports never finish a session.

Restart (`restart`, `tN`): only when the user asks (the pane has a Restart button with a confirm press for every open thread, and Restart desk for the desk): the thread's session is stopped (a working one too: its current step is lost; only a session in the thread's own folder) and a NEW session starts with the same handover (reason "Restarted from the pane."), same model and effort. Use it when a thread's context has grown large; nothing restarts a thread by itself mid-work. For the desk itself, the user presses Restart desk (or types /lean-agent-restart-desk): the handover is written to `~/.lean-agent/desk/handover.md` and a new desk session is opened. The old desk stays open (the mod cannot close a desktop session): the new desk's first notice names it and says to archive it in the Claude app (right-click, Archive), once per desk turn until it is gone; `lean_doctor` `dismiss-old-desk` ends the reminder.

Closing: when a thread reports done and the user needs nothing more, close it yourself (`close tN`) and clear its goal (`goal-clear`). Never ask a thread to close itself: it cannot, it only reports done.
