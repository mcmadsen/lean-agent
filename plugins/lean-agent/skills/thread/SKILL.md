# Threads

Threads are background sessions in `~/.lean-agent/threads/tN`. Touch them only through `lean_thread`; never run `claude --bg` or `--resume`. Report what the tool returned.

| action | input | effect |
|---|---|---|
| `new` | `title`, `project?`, `text` (brief), `model?` (haiku/sonnet; opus: see below), `effort?` (default medium: high only for design and refactoring), `needs?` (MCP servers/plugins on top of the project profile), `keep?`, `review?` ({pr\|branch\|sha, base?}: a review thread), `pr?` (number or URL: the PR the thread is started FOR; it then owns it, a mention in the brief does not) | creates and starts the session; workers may read and edit: brief them with `job:` and one step (`allowEdit` / `allowCmd` are accepted and ignored) |
| `send` / `wake` / `resume` | `tN`, `text?` | `send` queues and wakes an idle thread once; a running one is never resumed. A finished thread (not keep mode) or one over its context limit gets a NEW session with a handover; so does a stale-version or unapproved-opus one |
| `restart` | `tN`, `text?`, `model?`, `effort?`, `reason?` | only on the user's request: stops the session, starts a new one with the handover (a parked thread reopens). `restart` takes `text` (alias `message`): put new instructions and new facts there; they are the last part of the new session's first prompt and win over the handover (the same for `reopen`, `start`, `wake`, `resume`). A field an action does not use is refused by name |
| `start` | `tN`, `model?`, `effort?`, `reason?`, `needs?`, `keep?` | starts a thread that has no session yet |
| `park` / `close` / `reopen` | `tN` | `close` stops a finished session, clears the goal, never deletes the folder; `reopen` of a closed thread starts a NEW session with a handover |
| `keep` | `tN`, `on?` | keep mode: follow-ups to a done thread resume it until its context passes the limit; offer it only for many small follow-ups |
| `keep-going` | `tN`, `on?` | when the user says "keep going / no asks": the mod continues the thread by script at every turn end that is not done, blocked or a question (also `keepGoing: true` on `new` / `start`) |
| `action-cancel` | `id` | cancels a covered reply that waits in its 30 s hold window (the pane has Send now / Cancel) |
| `list` | none | state, running / idle / stuck, queued, model, `ctx` size, agents |
| `find` / `ask` / `report` | `text` / `tN` + `text` / `tN` | answered from the store with no model turn (or a small fresh one), never by waking an old session |
| `dismiss` | `tN` [`kind`] or `notice` | only after the user said so: hides tN's current Needs-you item (or `kind`: question, prompt, approval, blocked, stalled, restart, ready, model, action), or a top line (`notice`: its id or `all`) until a newer one arrives; nothing is answered |
| `goal-set` / `goal-clear` | `tN`, `text` | the thread's one-line goal (the chaser watches it) |
| `profile` | `project`, `mcp?`, `plugins?`, `fill?`, `on?` | the project's MCP/plugin allow-list (outside it: deferred, not removed); `fill: true` learns it from usage; a PR thread gets `needs: ["azure-devops"]` |
| `projects` / `project-add` / `project-remove` / `project-private` | `project`, `path?`, `on?` | registry; `projects all: true` includes private ones; turning private off needs the user's yes first (AskUserQuestion), then `confirm: true` |
| `action-list` | none | the remote writes threads asked for with an `action` request, each with the exact question to ask the user; and the user's active standing approvals (a status change they cover is sent by the mod at once: do not ask again) |
| `approve-action` | `id` | ONLY after the user chose Approve in AskUserQuestion for that request: the mod sends exactly the approved text once (a `batch` request: all its numbered writes, in order, stopped at the first failure, reported per item). Refused without a human Approve, when denied, expired (2 h), sent already or changed |
| `allow-writes` / `revoke-writes` | `tN`, `target` `{pr \| workitem}`, `kinds?` / `tN` or `id` | approval in advance: ONLY when the user's own typed words name that PR (number or URL) or work item and ask for the work ("fix the comments on PR 42"); the mod checks its record of their prompts and refuses otherwise (then ask with AskUserQuestion). A URL (PR with GUIDs, work item, GitHub PR; its org / project must be the thread's) names its target by the number at its end; `{workitem: "new"}` is the user's ask for a NEW work item (create). A grant covers that thread's reply / status / comment / link (work item: comment / update) on that target for 24 h, at most 40 writes: the mod sends them at once. Say in one line what it covers and that `/lean-agent:revoke tN` or the pane's Revoke takes it back. Never a target the user did not write; never for a push, merge or delete. A refusal says what the mod can see and carries a canonical question; `allow-ask` (`tN`, `target`, `kinds?`) returns the same: ask it with AskUserQuestion pasted exactly, options Allow / Not now: the user's Allow is the written yes (the mod reads it). Never give a slash command in a bash code fence (a Run button runs it in a shell, unseen by lean-agent): plain text |
| `allow-self-edit` / `revoke-self-edit` | `tN` / `tN` or `id` | a thread whose worker call the classifier denied may edit its registered worktrees itself (its own Edit / Write / Read / Grep / Glob, 24 h, never lean-agent's own state): ONLY when the user's recorded words (last 24 h) name the thread and say to let it edit / do it itself; the mod refuses otherwise (then ask with AskUserQuestion "Let tN edit its worktree itself?"). Say in one line what it covers and that `/lean-agent:revoke-edit tN` or the pane's Revoke takes it back |
| `deliver` | `tN`, `file`, `to`, `name?` | the mod copies a file from the thread's `scratch/` (or its worktree, or the desk reports folder) to `Downloads`, `Desktop`, `Documents` or a folder under the user's home; never overwrites (-2, -3); only when the user's recorded words name the folder or say save / put it in, else the reply is the AskUserQuestion to ask (exactly); on macOS EPERM the reply names the System Settings switch |
| `approve-push` / `push` | `tN`, `sha` (full), `reason?` / `pr?` | ONLY after the user explicitly approved that sha and branch in the chat. `approve-push`: single use, 2 h, signed. `push`: the desk pushes the approved commit (never forced, never a tag) from the thread's registered worktree, opens the PR with `gh` / `az` when `pr` is given, or answers with the host's create-PR link. Refused with the reason unless the project is not private, the worktree's HEAD is `sha` on an unprotected non-default branch, a full green review exists for `sha` and the approval is valid. The reply names what happened |

Rules:
- Opus: never choose opus (or any model that is not haiku or sonnet); only when the user wants it, pass `model: opus` + `reason`. The thread does NOT start: the request waits in the pane's "Needs you" for their Approve press (no tool call or message approves). Deny or no answer: `start` on sonnet when the user says so. A call that names no model for a thread recorded on an unapproved opus starts a new sonnet session. Do not ask for the press unless the reply says a request waits.
- Writes under an `allow-writes` grant are sent by the mod without a question (the thread's report says so): do not ask the user again for what it covers; a request outside it is asked as above. A thread requests actions as before.
- A blocked report that says "no permission prompt exists" (the classifier denied a worker call): when the user said yes in chat, call `allow-self-edit` (tN); if refused, ask with AskUserQuestion "Let tN edit its worktree itself?" and the options the report names; never tell the user to press Open unless the report says a prompt exists.
- A file the user asked for in Downloads / Desktop / Documents: the thread writes it to its `scratch/`, you call `deliver`; a question the mod returns is asked exactly with AskUserQuestion, then call `deliver` again.
- Reports reach the desk by themselves. A question: AskUserQuestion, then `send` the answer. A blocked report with an `action` request: `action-list`, ask with its exact question (options Approve / Deny / Edit first), `approve-action` only after Approve. Never call `approve-action` on your own, never fill `answers`. A blocked report with an `approval` (a denied action) is not a question: never ask it, never `send` a yes (it does not satisfy Claude Code's permission check); say once to press "Open tN" in the pane.
- Review comments: ado-pr-comment / gh-pr-review-comment with file + line (only on lines the PR adds or changes: the mod checks), several as one batch; one issue per comment, no coverage disclaimers.
- Review writes (all asked, with org, project, repo, pr): ado-pr-vote {vote approve|approve-with-suggestions|reject|reset|wait-for-author}, ado-pr-update {title?, description?, draft?, status? active|abandoned; never complete / auto-complete / merge options}, ado-pr-reviewer {op add|remove, reviewer, required?}, ado-pr-policy-queue {evaluationId}, ado-pr-workitem-unlink {workitem}, ado-pr-label {op add|remove, label}.
- Forge writes: never curl / az / gh a forge write; request the action kind (ado-pr-reply, ado-pr-thread-status, ado-pr-comment, ado-workitem-comment, ado-workitem-update, ado-workitem-create, ado-pr-workitem-link, gh-pr-comment, gh-pr-review-comment, gh-pr-thread-resolve, batch). A reply can carry `status` (one approval for reply + resolve); several writes for one PR are one `batch`. Never brief a thread to curl / az / gh a forge write: a `new` / `send` text that does is flagged.
- Forge reads: a thread reads PR threads / builds / work items with its run tool (get, ci) or the allowed az / gh read commands; never a token in a shell command.
- Done ends the session (the tick stops it, "tN finished"). Close a done thread when the user needs nothing more; never ask a thread to close itself.
- Context diet (a thread's guide says it; brief it the same): run the full test suite once per step, targeted runs in between; read diffs with --stat and one path; never read a notes file in full: headings first.
- `stuck` or "queued, session idle" means nobody read the message: `wake` (replaces a stuck session whose turn ended), or `restart` (the only way to replace a stuck session that still works: its step is lost, say so first). Never say "running" when the list says idle or stuck. `waiting for your answer` means the thread asked a question and did nothing since: answer it with `send`; the mod delivers it straight to the session and restarts the thread itself if it does not react (never ask the user about that).
- Skills a brief can name: `learn <project>`, `review-learn`, `compare`, `rules-pr` (branch `chore/claude-rules-<date>`, reviewed, then the usual approve-push with `pr.draft: true`; after the merge `send` the thread to run its last step).
